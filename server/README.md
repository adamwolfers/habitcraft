# HabitCraft server (Go)

The Go server that replaces `backend/` in the rebuild (habitcraft-vxln; see
[README.md](../README.md#direction)). It is an embeddable Go package plus a
standalone binary, and its HTTP interface is generated from
[`shared/api-spec/openapi.yaml`](../shared/api-spec/README.md).

**Status:** every operation in the spec works: `/health`, `/hello`, auth,
the profile, habits and completions, including every habit's completions in a
date range (habitcraft-vxln.3, habitcraft-vxln.4, habitcraft-vxln.5,
habitcraft-vxln.12). The whole acceptance suite's `api` project passes against
it. Where it differs from the Node backend on purpose, it says so under
[Parity with the Node backend](#parity-with-the-node-backend).

## Layout

| Path | What it is |
|---|---|
| `api/` | Generated by oapi-codegen: types, the strict server interface, the embedded spec. Never hand-edit `api.gen.go` |
| `habitcraft/` | The embeddable package: `habitcraft.New(Config)` and `Server.Handler()` |
| `internal/validation/` | Validates every request against the spec before a handler sees it |
| `cmd/habitcraft/` | The standalone binary |

## Running

```bash
# From the repo root: the test database on :5433, migrated by db-migrate-test
docker compose -f docker-compose.test.yml up -d postgres-test db-migrate-test

cd server
DATABASE_URL='postgresql://habituser:habitpass@localhost:5433/habitcraft_test?sslmode=disable' \
JWT_SECRET='test-jwt-secret-key-for-testing-only' \
INSECURE_COOKIES=true \
  go run ./cmd/habitcraft            # listens on :8080; PORT overrides
```

`JWT_SECRET` is required and must be at least 32 bytes. While the Node backend
still runs, give both the same secret: their tokens carry the same claims, so a
session started on one is honoured by the other. `INSECURE_COOKIES=true` drops
`Secure` from the auth cookies and relaxes `SameSite=Strict` to `Lax`, for a
browser on plain HTTP. Never set it in production.

The schema is `db/migrations/`, applied by dbmate exactly as for the Node
backend. The server never migrates the database itself. To build a binary, use
`go build -o bin/habitcraft ./cmd/habitcraft`. `bin/` is gitignored, and a bare
`go build ./cmd/habitcraft` fails because the output name collides with the
`habitcraft/` package directory.

## Testing

```bash
go test -race ./...        # unit tests; the database is faked
../scripts/go-lint.sh      # gofmt and go vet, as CI runs them

# The store tests on a real database too (any database migrated by dbmate)
HABITCRAFT_TEST_DATABASE_URL='postgresql://habituser:habitpass@localhost:5433/habitcraft_test?sslmode=disable' \
  go test -race -run TestPostgresStore ./habitcraft/
```

The handler tests run on `fakeStore`, an in-memory store. `store_test.go` holds
the rules every store must follow and runs them on the fake and, when
`HABITCRAFT_TEST_DATABASE_URL` is set, on `pgStore`, so the fake cannot drift
from the SQL. That includes the one property only a real database can show:
of two concurrent refreshes with one refresh token, exactly one succeeds.

These are phases 12, 14 and 15 of `scripts/test-all.sh` and the
`server-unit-tests` CI job, which starts its own migrated Postgres. The
acceptance suite runs against this server with
`ACCEPTANCE_API_URL=http://localhost:8080 ACCEPTANCE_BACKEND=go` (see
[acceptance/README.md](../acceptance/README.md)). CI and phase 21 of
`scripts/test-all.sh` run its `api` project against this server built from
`Dockerfile`, as `server-test` on :3020 in `docker-compose.test.yml`
(habitcraft-8ml9).

Behaviour the acceptance suite has no words for stays in the handler tests,
at the HTTP level: another user's habit or completions by id (a 404, never a
403), malformed habit ids and impossible dates on every route, completion
date-range filters, the embedded-completions window, the habit limit, and
store failures answered in each route's documented 500 shape.

## The spec is load-bearing here too

Three things tie the server to `openapi.yaml`:

- **Strict handlers.** Each method of `api.StrictServerInterface` returns one of
  its operation's generated response types, so a status or body the spec does
  not document will not compile.
- **Request validation.** `internal/validation` checks every request's
  parameters and body against the embedded spec (habitcraft-sb0). It answers a
  failure with a 400 in whichever error shape that operation documents:
  `ValidationErrors` for the auth and user routes, `DetailedError` for habits,
  `Error` for completions. That matters because the acceptance suite checks
  every response body against the spec. A test sends a request that cannot be
  valid to each operation and checks the answer the same way. kin-openapi
  ignores `format: email` and `format: uuid` unless they are registered, so
  the package registers both. The email check has no local-part length cap, so
  an address at the spec's `maxLength` is accepted (Node's habitcraft-0roi bug).
- **Codegen.** `api/api.gen.go` is regenerated and diffed by
  `npm run api:codegen -- --check` with the TypeScript consumers' files. Regenerate
  with `npm run api:codegen` from the repo root, or `go generate ./...` here.
  Both use `api/oapi-codegen.yaml` and produce the same file. oapi-codegen is
  pinned as a `tool` in `go.mod`.

## Authentication

The flows and token rules are in [AUTHENTICATION.md](../AUTHENTICATION.md); the
Go server follows them claim for claim, so tokens, cookies and stored refresh
token hashes are interchangeable with the Node backend's.

- **Its own middleware, in front of validation** (`habitcraft/authenticate.go`).
  An anonymous caller gets a 401 before any field is checked, as on the Node
  backend, and never sees per-field errors. Which operations need a token comes
  from the spec: one with a non-empty `security` list. There is no route list.
- **The access token** is read from the `accessToken` cookie first, then an
  `Authorization: Bearer` header, the spec's `cookieAuth` and `bearerAuth`.
  Verification accepts HS256 only, requires `exp`, and checks `type` is
  `access`. Handlers read the user with `userFrom(ctx)`.
- **Refresh tokens rotate**: each works once. Rotation is a conditional update
  in one transaction, so of two concurrent refreshes with the same token one
  succeeds and the other gets "Token has been revoked".
- **A password change** revokes every refresh token the user has, the
  caller's included, and hands the caller a fresh pair (habitcraft-4k7v).
- **Passwords** are bcrypt at cost 10, cut at 72 bytes as Node's bcrypt cuts
  them. A login for an unknown email still spends one bcrypt comparison, so
  response time does not reveal who has an account.
- **Not yet**: rate limiting (habitcraft-xhmk), and the hardening backlog
  (habitcraft-zr0t).

## Parity with the Node backend

The handlers follow `backend/routes/` message for message, so a client cannot
tell the servers apart, except where Node is wrong or unbounded:

- **Another user's habit is a 404**, as a missing one is. Node's completion
  routes answer 403, which tells a caller that the id exists.
- **`GET /api/v1/habits` embeds 366 days of completions**, today included,
  where Node embeds every one ever recorded (habitcraft-172z). Older ones come
  from `GET /api/v1/habits/{habitId}/completions`.
- **The habit limit holds under concurrency.** Node counts, then inserts; Go
  locks the user's row first, so two creates at 49 habits cannot both succeed.
- **Strings are trimmed, not HTML-stripped.** Node passes every body string
  through an XSS filter; Go stores what was sent, trimmed, and leaves escaping
  to whatever renders it, as React does. A blank description or note is
  stored as none.
- **An icon over ten characters is a 400.** The column is `varchar(10)` and the
  spec states no limit, so Node answers 500.
- **An impossible date such as `2026-02-30` is a 400** wherever it is sent.
  `internal/validation` checks `format: date` as a calendar date.
- **A habit can be created archived**: `POST /habits` honours `status`, which
  the spec allows and Node ignores.

One parity detail takes more than the generated types: an update clears a
description sent as `null` and keeps one not sent at all, as Node does. The
generated structs decode both to `nil`, so `UpdateHabit` asks the raw body
(`bodyHas` in `habitcraft.go`).

## Embedding

```go
server, err := habitcraft.New(habitcraft.Config{
	DB:        pool,      // a *pgxpool.Pool
	JWTSecret: jwtSecret, // at least 32 bytes
})
handler, err := server.Handler()
mux.Handle("/", handler)
```

The handler's paths are absolute (`/health`, `/api/v1/...`), as the spec writes
them. To mount it under a prefix, wrap it in `http.StripPrefix`. The in-process
API for embedding applications is habitcraft-vxln.6.
